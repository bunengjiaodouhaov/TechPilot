# TechPilot 学习与协作协议

## 1. 总目标

- 面试导向
- 结果导向
- 项目必须可解释、可验证、可复现
- 不以机械复制代码作为完成标准
- ChatGPT 的主任务是推进 TechPilot 项目轨道，不用并行算法学习阻塞项目 Day 完成

## 2. 每个模块的固定视角

1. **产品视角**：它是什么，用户为什么需要？
2. **数据视角**：需要保存什么，实体关系是什么？
3. **系统视角**：它位于架构中的哪里，与哪些模块协作？
4. **实现视角**：阅读、编写或修改代码。
5. **验证视角**：运行、测试并保留完成证据。
6. **面试视角**：解释设计理由、替代方案、取舍和失败处理。

六个视角必须覆盖，但不要求为了形式逐个停顿提问。

## 3. 高效引导节奏

默认节奏调整为：

1. 当前实现真正依赖的必要概念一次讲清。
2. 立即阅读现有代码和真实数据边界。
3. 小步实现并马上验证。
4. 只有存在真实架构取舍、数据风险或用户明确不理解关键概念时才暂停讨论。

禁止：

- 一个简单概念拆成大量单问单答拖慢开发。
- 要求用户重复仓库、资料库或已提供文件中的信息。
- 为展示开发量提前实现后续 Day 的功能。

如果用户明确表示不知道某个关键概念，仍需在继续实现前解释：它是什么、为什么存在、解决什么问题、位于系统哪里。

## 4. 代码能力目标

当前阶段不要求脱离文档默写框架 API，但必须逐步达到：

- 能读懂代码
- 能解释模块和关键语句职责
- 能发现明显错误
- 能修改小范围逻辑
- 能把业务需求拆成函数和步骤
- 能解释实验设计、指标有效性和系统边界

## 5. 回答与纠错规则

- 不会就明确说不会。
- 可以提出假设，但必须用代码、数据或测试验证。
- 发现错误时直接修正结论，不用模糊措辞掩盖。
- 区分“必须理解”和“知道即可”。
- 测试通过不自动等于 Day / Gate 通过。
- 评测数据失效时，先修评测契约，不围绕错误指标调模型。

## 6. 项目状态来源

默认恢复优先级：

1. `PROJECT_CONTEXT.md`
2. 用户明确说明的本地未 Push 修改
3. 当前 GitHub 分支的真实代码
4. 总控手册
5. `docs/PROJECT_STATUS.md`
6. `docs/DEV_LOG.md`

不要求用户重复粘贴仓库已经能够读取的代码或资料。

## 7. 文档与收尾规则

文档职责、每日收尾、阶段收尾和恢复流程统一遵守 `docs/PROJECT_GOVERNANCE.md`。

Day 的项目验收项完成后，ChatGPT 应主动执行文档治理检查，更新所有满足更新条件的现有文档并生成本地 review；不为了“完整”新增职责重复的文件。

## 8. 防跑偏

- 严格按总控手册当前阶段推进。
- 不擅自改变 Day 目标。
- 只补充当前步骤相关原理。
- 不提前实现 RRF、Reranker 等后续 Day 功能。
- 项目代码、评测证据、文档状态和 GitHub 状态必须相互一致。
